This postmortem answers an orientation question, so the map comes first and the findings follow from it.

The layers. VISION.md owns the why: an engine that turns any input into a deterministic scene. Determinism is the measuring instrument, and "declarative" is a claim about structure, not about writing style. docs/representation.md owns the decision from August 2 that makes the claim concrete: data is anything you can check without running the scene, every spot where checking must stop gets declared out loud, and the shared kit is generated from one source. docs/plan.md owns the architecture and the phase gates, including the REP0 to REP6 track that carries out the representation decision step by step. docs/working-plan.md owns the tactical layer: tracks that cut across phases, deferred items with the conditions that revive them, and the day-to-day queue. docs/README.md routes between all of them.

The difference between plan and working-plan. Both files state it, and each points at the other. docs/plan.md (line 13): "This file owns the architecture and the phase gates. The current tactical plan … lives in working-plan.md. Most of that work is cross-phase: it serves every phase and belongs to none." docs/working-plan.md (line 17) points back: "plan.md is the founding architecture and its phase gates. This is the consolidated tactical plan." Its mapping table sends each tactical track to the phase whose gate governs it, on the stated principle that "an item that maps to a phase inherits that phase's gate." So the pair is not two versions of one document. One holds strategy with gates, the other holds the queue with triggers, and they stay consistent because each declares which file wins, not because anyone keeps their text in sync.

Is the pair maintained? Yes, and you can measure it. Both files carry freshness markers current to the range (plan.md 2026-08-03, working-plan.md 2026-08-04). working-plan.md's header carries a verified status column, added after one of its own annotations asserted a state that turned out false. The REP stamps in plan.md were written at landing time on both days. The queue section in working-plan.md moved to LANDED within hours of 0.18.2 shipping (internal/log/log_2026-08-04.md). Corrections get logged instead of made silently: 9f94ab2 corrected a hand-written count in the day's log the same evening someone wrote it.

1. What went well

  • The whole span was one coherent motion on the representation track. August 3, morning: the 0.17.3 parity findings closed, each proven red before the fix. Midday: REP2 landed (6f656c1, merged as PR #10 at e5d73e9). check now executes the canonical fence store instead of keeping its own copy of the rules, and bracket-check-kit.js holds that gate by running four divergence cases through both instruments. Evening: the corpus bracket landed as 0.18.1 (f2ad67b). August 4: the review's three behavioral findings closed as 0.18.2 (e4cd60f), each fix's test arm recorded red first. Every step turns a line of the representation decision (declared holes, or the kit generated once) from prose into enforcement.
  • The review protocol converted directly into shipped fixes. The August 3 four-pass review found all three behavioral defects through its adversarial pass (docs/postmortems/2026-08-03_session_rep2-review-protocol.md). The session deliberately kept them out of the merge, queued them with their mechanisms in working-plan.md, and closed them within 20 hours as 0.18.2. Report and repair stayed separate motions, both recorded.
  • The plan pair absorbed the churn without drifting apart. REP2's stamp, the working-plan queue section, the router's work-next row, the site's REP card, and the CHANGELOG were each updated at their own landing moments: five surfaces, one version of events. The single miss is filed under Escapes.
  • A VISION criterion that was honestly failing moved. VISION.md records "a declaration can be validated before a frame is rendered" as only partly true. Both days strengthened exactly that criterion: REP2 made the validator run the kit's real semantics, and 0.18.2 made every remaining substitution announce itself (internal/log/log_2026-08-04.md). The criterion's honest boundary, that extents need runtime geometry, is unchanged and stated in VISION.md itself.
  • An unplanned rule earned its adoption on measurement. The cite-or-label rule (4cee16e) was adopted mid-span after the August 3 review measured the session's own summary prose as its least reliable artifact: seven drift findings on hour-old writing. Its reminder hook fired on August 4's record surfaces and caught a claim written before it was true (internal/log/log_2026-08-04.md, the "selfcheck green" incident).

2. What did not go well

  • The cleanup sweep after 0.18.2 missed the architecture document. The August 4 landing updated docs/README.md, site/index.html, and working-plan.md, but docs/plan.md lines 1048 and 1060 still called the landed cascade "the 0.18.1 cascade" and "the 0.18.1 queue". Those lines went stale the moment 0.18.1 was assigned to the corpus bracket instead (f2ad67b), and only this postmortem's evidence pass found them. The lesson that transfers: a version number written into a stamp is a state claim. When the number moves, every stamp naming it becomes wrong, and only a grep for the number itself finds them all. A remembered list of status surfaces does not.
  • The superseded-parts hazard in working-plan is managed, not solved. Its own header records a fresh session reading 460 superseded lines before discovering that the restructure plan wins (docs/working-plan.md header). The mitigation is a warning block plus the router. The actual fix is docs/restructure-2026-07.md deleting itself when its last gate goes green, which has not happened yet because R5 remnants remain open.
  • The label collision is a standing comprehension tax. One letter means three things: R0 to R5 are the restructure gates, Phase R is plan.md's restructuring phase, and REP0 to REP6 is the representation track. docs/README.md's work-next row carries a "label key" precisely because of this. The orientation question that prompted this postmortem is the cost showing up live. This next part is inference, not measurement: renaming now would churn more of the record than it clarifies, so the key in the router is probably the right ceiling.

4. Escapes (tests)

  • The three 0.18.2 defects escaped check's own test suite by being green-but-blind. bracket-commands.js had a test arm for every property check claimed to decide, but no arm exercised a bible STYLE with match/fov, an unresolved anchor fraction, or a dot-assigned table. So check stayed green while wrong in three ways. The adversarial review pass caught them instead (docs/postmortems/2026-08-03_session_rep2-review-protocol.md). Each case now has an arm, and each arm was watched go red against the pre-fix code (internal/log/log_2026-08-04.md).
  • The stale plan.md pointers are a process escape from August 4's own cleanup grep. The grep listed status surfaces from memory instead of searching for the moved token ("0.18.1") across all tracked prose. No mechanical check covers version pointers inside planning prose, and that is by design (scripts/derived-counts.js excludes the planning documents). So the control here is the procedure, and the procedure's scope was the defect. Fixed in the same commit as this postmortem.
  • The tests added in the span carry recorded claims: the six bracket-check-kit.js arms and the two new bracket-commands.js arms each state what they pin, and CHANGELOG.md 0.18.2 records the red-first runs.
